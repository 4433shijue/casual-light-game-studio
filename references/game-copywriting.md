# 世界观用语与游戏文案

当用户需要命名、界面提示、物品说明或文案检查时读取本文件。它可以独立使用，也可以参与玩法、UI 和资产设计。只做当前请求需要的部分，案例和表格随时可改。

## 从当前任务开始

先利用已有设定、功能说明、界面和项目术语。只有缺失信息会改变结果时才追问；一句世界设定加几个功能，也足够开始小范围设计。

- 整套设计时，整理体验气质、实际机制和说话者，再确定用语方向，展开常用文案。
- 局部命名或改稿时，直接处理指定内容，简述含义与必要的关联影响，不启动完整策划或强制建表。
- 检查已有文案时，指出具体位置、理解风险及建议改法，保留仍适用的已定称呼。

方向不明且值得讨论时，给出三种有实质区别的语言方向，例如日常职业感、民俗气质、轻松怪诞；说明各自怎样影响理解和氛围。用户要求直接生成时，采用合理假设并明确标注，不另设选择关卡。已选方向和用户提供的名称优先。

## 让称呼对应真实功能

从实际功能找概念，再为它取名。角色身份可以来自职业、能力来源或社会关系；资源可以来自世界中的用途与取得方式；任务、地图、成长和活动也按相同思路处理。没有的系统不补造。玩家控制的角色、可招募成员和故事 NPC 不一定属于同一种身份。

一个好用的候选需要解释得通、容易区分，并能容纳已知的后续内容。简短说明取名依据及可能误解，必要时提供普通叫法作为对照。不要假称名称已经经过商标查重或全球唯一性检查。

同一个功能保持一致称呼。不同功能共用一个词时，先判断是否真有同一含义；存在混淆就给出区分方案。世界内人物可以使用昵称，界面仍需能对应到同一个对象。

首见术语需要时配合动作或短解释，例如“待投信件”下写“选择一封信，查看投递路线”。返回、退出、音量等普通用语可以保留，不必要求玩家先考过世界观阅读理解。

## 按使用位置写

| 位置 | 写作依据 | 交付时关注 |
| --- | --- | --- |
| 按钮与菜单 | 点击后的真实动作 | 标签直接，确认按钮能辨认结果 |
| 教学与任务 | 当前输入方式、触发条件和目标 | 先告诉玩家做什么，不编造按键或奖励 |
| 反馈与空状态 | 成功、失败、等待或确实没有内容 | 说明发生了什么，适用时给出下一步 |
| 技能与道具 | 已知效果、数值、消耗、限制 | 机制说明可单独读懂，风味描述适量补充 |
| 角色与叙事 | 身份、目标、关系和知情范围 | 台词属于当前人物，避免人人同一种口吻 |

系统提示、角色对白、世界内组织公告可以有不同声音。同一页面优先保持称呼一致；角色的玩笑不能遮住系统必须说明的事实。

退出、删除、付费和不可逆操作要写清对象、代价及后果，不能只给诗意标签。尚未核实保存行为时，不承诺“进度已保存”；尚未确定失败损失时，不编造“道具全部保留”。缺少规则就标为待核对，并提供不承诺未知后果的临时文案。

数值与条件按提供的机制或当前实现写，不能为了顺口改变效果。需要代码接入时沿用现有文本键、占位变量和本地化方式；仅改文案不要自动更改代码标识、资源路径或存档字段。

界面有长度约束时可提供短版与完整版。有实际界面才检查字体、换行、遮挡及目标屏幕；字符数只做初步估计。没有运行证据时写明尚未验证显示效果。多语言只在用户需要时展开，保留变量和实际意义。

## 三个虚构案例

以下设定用于演示选择方法，均可改写或跳过。它们不是新增系统清单。

### 幽灵邮局

假设玩家夜间送信，有投递委托和路线，没有体力、等级与招募。语气温和，带一点夜班打工人的疲惫。

| 实际功能 | 候选文案 | 依据或边界 |
| --- | --- | --- |
| 玩家身份 | 夜班邮差 | 身份来自工作，无需假设战斗能力 |
| 任务列表 | 待投信件 | 列表中每项确实是一封待投递的信 |
| 选择路线 | 投递路线 | 地图按送信路线组织才适用 |
| 没有可接任务 | 今夜的信已送完。歇会儿吧，门铃还没响。 | 仅在已完成投递且未来会有新信时使用 |
| 教学 | 点选一封信，查看收件地址。 | 假设点选确实打开地址信息 |
| 设置 | 声音设置 | 不必改成“聆听彼岸” |

如果用户希望增加灯油，可以提出它可能怎样服务体验；当前文案任务不能直接把灯油写成既有体力资源。剧情失败可以写“这封信还没找到归处”，但是否保留进度必须另按实际机制说明。

### 阳台小茶摊

假设游戏包含接单、配茶、收款和熟客关系。风格亲切，菜单一眼能看懂。

| 实际功能 | 候选文案 | 依据或边界 |
| --- | --- | --- |
| 今日订单 | 今日茶单 | 订单确实以茶饮为主 |
| 金钱 | 茶钱 | 用于购买原料，不与熟客关系混称 |
| 顾客关系 | 熟络度 | 表达关系进展，不能当作可花费货币 |
| 开始营业 | 开张 | 短按钮，对应营业状态切换 |
| 原料不足 | 茶叶不够了，补齐后再泡这一杯。 | 要确认实际缺的是茶叶，不能把所有缺料都这样写 |
| 删除存档 | 删除存档 | 确认页按实际行为解释删除范围及可否恢复 |

角色可以说“这杯我能等，老板别把自己泡进去了”。系统仍要清楚显示订单是否有时限，不能让玩家把安慰当作规则。

### 无目标的风与色

假设鼠标拖动会搅动色带、滚轮调整风速，没有角色、任务、分数和结束判定。

只需“拖动，拨开颜色”“滚动滚轮，调整风速”，以及“重新铺开”“声音”“退出”等少量文案。“重新铺开”只有在按钮确实重置画面时适用。

可以提出更安静的呈现方式，例如第一次交互后淡出操作提示。是否采用由当前体验目标决定，不为填满模板增加称号、货币或通关祝词。

## 记录与后续修改

持续项目可使用 [术语与文案记录模板](../assets/templates/game-lexicon.md)，优先更新已有同类记录。按需求交付候选、采用稿或待核对项；没有用户选择或明确委托定稿时，不把建议写成已确认事实。

改名时检查相关界面、教学、任务与物品说明，必要时连同配音、图片内文字和生成提示词一起列出影响。局部改稿只检查涉及部分，不自动全库替换同名字符串。代码键与存档名称通常保持原样；确需迁移时单独说明原因并按本次授权执行。

交付内容随任务大小调整。几处改名给出候选和理由即可；整套工作可附术语表、按场景整理的文案和少量待确认问题。对比稿要能看出哪些是原文，哪些是建议。不要用表格数量或检查分数评价创意质量。
