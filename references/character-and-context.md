# 角色声音与情境文案

只读取当前任务需要的部分。角色声音、动态提示、短事件都可单独处理，用户只要一句就交付一句，不强制创建角色档案或剧情数据库。

## 让说话者在当前情境中说话

利用已有身份、关系、目的、知情范围和情绪决定称呼、表达直接程度、信息取舍与句子节奏。角色能误解或撒谎，但必须符合当前剧情，不能无意泄露他尚不知道的事实。保留已定人物，不因新模型偏好的语气重写性格。

口头禅可用但不承担全部区分。同一角色面对朋友与陌生人可以改变措辞，同时保留稳定的行为倾向。下面是虚构例子，谨慎的邮差需要阻止别人进入一条断桥路线。

| 对象与目的 | 候选台词 |
| --- | --- |
| 熟悉的同伴，直接拦住 | “先别走那边，桥断了。我陪你绕过去。” |
| 初次见面的顾客，解释改道 | “那边的桥暂时过不去，我带您走另一条路。” |

两句话共享信息与谨慎态度，关系改变表达方式。身份、桥梁状况和路线都是例子，不自动写进用户设定。冷峻、童话、荒诞或简洁风格均可，不能因为指南有玩笑就让所有角色说段子。

## 首次与重复提示

先确认触发条件、提示对象、已有进度和重复次数是否有真实依据。缺少运行规则时给出候选方案，并明确哪些条件需要实现；写好文案不表示计数、冷却或触发系统已接入。

首次提示可解释动作与原因，熟悉后的提示可以缩短；关键消耗、不可逆后果与当前错误原因仍需清楚。依据项目需要选择重复间隔、变体或不再显示，不默认设计一套复杂提示管理器。不要为变化而随机遗漏关键事实。

假设真实机制是缺少 {missing} 片茶叶就不能制作，此处花括号仅演示变量写法，接入时遵循项目原格式。

| 场景 | 候选系统提示 |
| --- | --- |
| 首次遇到缺料 | “还缺 {missing} 片茶叶，补齐后才能制作。” |
| 再次遇到同类缺料 | “茶叶不足，还缺 {missing} 片。” |

店员可以另说“水烧好了，茶叶还没上班”，但系统仍要说明实际缺料数量。删除存档即使提示过多次，也不能缩成“再见啦”而不说明删除对象和后果。撤销、保留进度等承诺必须符合实际机制。

## 短事件与分支选择

从事件发生条件、角色当下目的、玩家可以做的选择及后果组织内容。只列任务真正需要的分支，标明已定事实与候选剧情，不擅自增加货币、关系值或结局系统。

已有任务状态或剧情变量时沿用，不为写对白自动改代码标识。选择文字应帮助玩家理解行动；有意隐藏结果须符合用户的叙事目标，不能意外把付费或不可逆操作藏成模糊台词。无剧情作品可以只写功能提示，不展开故事。

## 工程接入与改稿

沿用现有文本键、占位符、数值、条件和输出格式。保留需要的转义与换行，长短版本按实际界面需求提供；没有界面验证就注明长度与显示效果待检查。用户只要稿件时不直接写入工程。

候选句、采用稿和已接入运行的内容分开描述。改稿只动当前范围，发现相邻冲突时说明影响，不自动扩大为全剧本重写。需要记录时可在已有 [术语与文案表](../assets/templates/game-lexicon.md) 增补说话对象、情境、重复条件和待实现项，不要求填写所有列。
