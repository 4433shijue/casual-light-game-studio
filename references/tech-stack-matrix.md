# 技术栈推荐矩阵

> 使用定位：本资料仅供启发与按需取用，可改写、组合或跳过。用户与智能体的创意决定方案；示例类型、数值、流程和结构不构成创作限制。技术操作的真实前提、执行授权与验证诚实性仍需遵守。

使用目标平台、输入、维度、复杂度、资产来源和用户经验筛选，不按表格机械决定。先推荐一个首选，再说明替代方案和切换条件。

| 场景 | 常见首选 | 优势 | 需要留意 |
| --- | --- | --- | --- |
| 免安装、双击文件分享 | 原生单文件 HTML | 不要求安装引擎或开发工具 | 单文件不自动等于离线，需按实际打开方式验证 |
| 网页与较多独立素材 | HTML 与素材目录 | 素材易替换 | 按加载方式决定是否需要本地服务 |
| 2D 浏览器、即时分享 | Phaser + TypeScript + Vite | 启动快、部署简单、适合短回合和 DOM UI | 原生桌面/移动能力需要额外封装 |
| 3D 浏览器、轻量展示 | Three.js 或 React Three Fiber | WebGL 灵活、便于网页展示 | 需要自行处理游戏状态、资源和性能边界 |
| 2D/3D 桌面和移动端 | Godot | 场景、输入、导出和资源管理完整 | 团队若不熟悉 GDScript 或 Godot 工作流需留学习成本 |
| 已有 Unity 经验或要更大内容量 | Unity | 生态和工具丰富，适合持续扩展 | 小型原型可能有较高工程和导出开销 |
| 纯规则、文字或极简交互 | HTML/CSS/JavaScript | 依赖少、迭代快、方便生成单文件 Demo | 动画、输入和复杂场景需要自行组织 |

## 推荐决策

- 先利用已有信息确认发布平台、环境、安装意愿、分享方式和玩家输入，缺少关键信息才问。触控、鼠标、键盘和手柄会改变 UI、判定和测试方式。
- 若核心是 2D、短回合和快速分享，优先比较 Phaser、Godot 和原生网页。
- 若需要桌面/移动导出、场景编辑、动画和存档，优先比较 Godot 与用户已有经验的引擎。
- 若需要 3D、物理或大量现成资产，评估 Three.js、Godot、Unity 的资产管线和性能成本。
- 若用户已有项目，先尊重现有技术栈，除非它无法支持核心需求或迁移收益明显高于成本。

## 最小项目结构参考

按实际引擎翻译这些职责：入口/启动、游戏状态、输入适配、核心规则、内容数据、渲染场景、UI、音频、资产加载、存档和调试。概念验证版可以合并文件，但要保留可替换边界。
