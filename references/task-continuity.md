# 任务范围与项目接续

以下是工作量判断参考，可按项目调整，不是固定审批流程。

## 本次要做多少

| 本次请求 | 合适的推进方式 | 通常无需重复 |
| --- | --- | --- |
| 一个问题或点子讨论 | 直接回答关键取舍，必要时给短例子 | 建项目、生成全套文档 |
| 调手感、修错误、加一个按钮 | 检查相关实现，局部修改，验证受影响行为 | 引擎选型、完整策划、无关系统审计 |
| 加敌人、关卡、玩法机制 | 核对与既有规则/数据的连接，增量实现与回归 | 重建工程、重写全部资产表 |
| 从零探索作品 | 识别创意和最大未知，给相称的方案或原型 | 自动生成所有模板、先锁死游戏类型 |
| 升级或发布 | 聚焦新增内容与目标平台要求 | 把所有 A/B/C 阶段从头再做一遍 |

先利用用户已提供的信息。已有代码时查看相关入口和调用方，不因为改动小就跳过必要核对。任务大也不意味着必须读完资料库。无法取得文件时，说明具体缺项，可以先给适用的修改建议，但不能声称代码已修复。

用户要求讨论时保持讨论；用户要求实现时落实实现。提问只针对无法合理推断且会改变结果的信息。普通实现选择由智能体处理，不将已有授权转成重复的“是否继续”。

## 接续记录何时值得写

长期项目在完成一个可玩里程碑、方向改变、发现重要限制或需要换会话接续时，记录当前状态。有项目写入授权时可更新项目内记录；只读咨询、微小措辞修改、单次问题不为了执行 Skill 创建文档。没有文件能力时提供简短交接摘要。

优先复用项目已有计划、决策或交接文件。没有同类记录且确实需要时，可使用 `docs/game-context.md`，或按项目惯例选择位置。不要在不同文件中各维护一份互相冲突的当前状态，也不要把项目状态写进全局 Skill 或个人记忆。

只保留对继续工作有帮助的信息：当前创意目标、用户明确选择、建议与待定项、现有可玩内容、验证证据、外部素材依赖、关键问题、下一步。参考模板可以裁剪，避免堆聊天原文。保存稳定的项目相对路径、测试命令和结果；未执行就是未执行。

## 下一次如何继续

1. 先读当前用户要求及相关项目约定，再读现有接续记录。
2. 对本次工作依赖的文件、功能和测试状态做低成本核对。只读旧记录时说清这是上次记录，不能视为刚刚验证。
3. 用户的新明确要求优先于旧决定。旧记录与代码不一致时写明差异并据此调整；不要擅自补造原因。
4. 沿用仍适用的技术、创意和约束，继续最小必要工作，不重新询问已确认的方向。
5. 重要变化后更新相关条目，已过时的下一步从当前状态移走；需要解释取舍时保留一句变更依据即可。

示例：记录说“浏览器版、无计分、音频待外部制作”，用户现在要求增加风向变化。先检查风向与声音映射所在实现，保留无计分设计；用临时声音继续调交互，把外部音频标为待回传。无需重做技术选型或强加关卡。
