# 用户指南

先说你想让玩家做什么，再说这次希望做到哪一步。想得不完整也可以，留一点空白给讨论。

## 第一次提需求

下面这些信息有多少给多少。平台、参考作品、输入方式和时间限制都能帮助判断；没有答案的地方，不用为了填表现场发明。

```text
使用 $casual-light-game-studio。
我想做一个整理旧物的小游戏，组合物品会揭开一段故事。
希望在浏览器玩，用鼠标操作，没有倒计时。
这次先讨论最小玩法，别写代码。
```

智能体可以帮你找最值得验证的问题，例如物件关联能不能被推理出来。它也可以提出新想法，不过建议应当清楚标出，不能默默把你的故事改成限时消除。

## 决定这次做到哪里

工作方式和作品规模是两回事。你可以先讨论一个完整作品，也可以直接实现一个极小原型。

| 工作方式 | 可以怎么说 |
| --- | --- |
| 方案优先 | 先整理方案，暂时不改文件 |
| 边设计边实现 | 每次做好一个小模块，再继续下一块 |
| 先做可玩骨架 | 直接做最小可玩版，资产先用占位 |

版本目标里的 A 表示概念验证，B 表示可展示 Demo，C 表示小型完整作品。按需求使用这些称呼即可，也可以用自己的里程碑。没有必要为一颗按钮举行版本晋升仪式。

## 缺资产怎么办

把期望画风、用途、参考材料以及当前工具能力说清楚。智能体支持生图时，可以做候选图与检查；不支持视频时，就整理提示词和交接规格，由你在外部生成。

```text
现在只准备资产交接包。
需要一张背景和一段结束动画，给我提示词、规格、命名和接入位置。
图片工具可用，视频工具不可用。
先给我看少量图片候选，视频等我外部生成后回传。
```

实际能力以工具可调用的情况为准。写一句“请生成视频”不会让文本模型突然多出摄影棚。

素材回传时附上用途和文件位置，让智能体检查规格、透明背景、动画时长或播放兼容性，再接入项目。候选图好看和游戏里好用，还要分别看一眼。

## 已有项目直接说改哪里

```text
这是现有游戏目录。
只修暂停后倒计时仍减少的问题，保留现有玩法和技术栈。
检查相关代码后直接修改，并验证暂停、恢复和重玩。
```

小任务应只检查相关路径。出现确实关联到存档、输入或资源的影响，再扩大检查范围。无需重新设计世界观来修计时器。

## 换会话继续做

持续项目可以沿用已有交接文档，也可以参考包里的 `assets/templates/project-context.md`。记录当前目标、真正完成的内容、验证证据和下一步就够了，聊天原文无需全文搬家。

```text
先读取项目现有接续记录，再核对本次修改涉及的代码。
我现在决定取消分数，改成自由体验，技术继续沿用。
只更新方案和接续记录，下一次再实现。
```

新决定优先于旧记录，但“决定取消”不等于“代码已删掉”。好的接续记录会把这两件事分清楚。

## 工具按需要用

以下命令在技能根目录运行。输出位置用新的目录或文件，脚本拒绝覆盖已有内容。

```bash
python scripts/create_starter.py godot ../my-godot-game
python scripts/create_starter.py phaser ../my-phaser-game
python scripts/scaffold_manifest.py ../my-assets.json --game my-game
python scripts/check_game_manifest.py ../my-assets.json
python scripts/generate_game_docs.py assets/templates/brief.example.json ../sample-docs
```

最后一条会用演示简报生成文档。做自己的项目时，先复制并改好简报，再替换命令里的输入路径。示例标题留在正式文档里，AI 可不会替你尴尬。

脚本检查字段、依赖和文件结构，无法检查故事是否动人。格式验证通过以后，创意仍然可以继续改。

## 验证时看两件事

先看游戏是否正确运行，再观察玩家能否理解、是否愿意继续。自动测试可以发现计时错误，玩家停在一个物件前半分钟的原因，往往还得问问本人。

使用 `assets/templates/playtest.md` 记录操作、观察和原话，状态没测就写未测。若核心体验不成立，先改机制，再考虑增加关卡。关卡数量暂时替不了乐趣值班。

## 让游戏说自己的话

文案分支可以单独使用。给出世界设定和几个真实功能，就能开始；已有项目还可以提供当前称呼、界面文字或需要调整的片段。只改两个名字，也完全够开工。

整套设计会考虑语言方向、常用术语和玩家实际看到的文案。局部需求直接处理指定内容。检查已有稿时，会说明哪里容易误解，并给出建议改法。风格拿不准时可选三种方向，也可以说“直接给我一版，假设写清楚”。

例如幽灵邮局的任务可以叫“待投信件”，但如果游戏没有体力，就不该凭空多出一管灯油。名字不能偷偷带着玩法进门。

系统、角色和世界内组织可以有各自的口吻。技能效果、删除范围和退出后的进度情况要按实际规则写。尚未核实的行为会保留待核对状态，不让一句漂亮话替程序作保证。

长期项目可维护 [术语与文案记录](../assets/templates/game-lexicon.md)，也可以沿用自己的文档。候选名称与已采用名称分开记录。需要改名时，检查相关界面、教学和资产提示词；仅改显示文字，不自动修改代码键和存档字段。

没有角色、分数和关卡的抽象小游戏，也可以只保留操作提示和少量设置文字。参考资料随便取用，空白栏目无需硬填。

## 环境与屏幕方向也由需求决定

告诉智能体你打算怎样运行和分享，是否愿意安装工具，以及主要用鼠标、键盘还是触屏。已经说明的条件不用再选一遍。没有 Godot 时，可以评估原生网页、单文件 HTML 或现有前端工程；开发工具与玩家需要的工具要分别说明。

单文件不保证离线。如果你要断网双击可玩，请直接写进需求，智能体应按这种方式验证。素材多时也可以采用文件夹交付，不必把所有内容都塞进一个 HTML。手机打开本地文件的情况需要单独核实。

横竖屏按视野、操作和设备推荐，也可以明确只支持一种。先决定玩家做什么，再安排信息和按键。代码结构可以借用，界面和玩法不必照搬；没有攻击就不用准备攻击键，按钮也想少加点班。

参考 [浏览器交付指南](../references/browser-delivery.md) 和 [布局指南](../references/layout-and-input.md)。附带 HTML 示例可以直接复制打开；用脚本创建仅是可选便利，需要 Python，示例本身不需要 Python。

## 调手感与看试玩反馈

描述一个具体动作和希望得到的感受，例如拖动紧跟手指、松手后轻轻落稳。智能体可以分析响应、吸附和表现的取舍，提供待试参数；参数没有实际运行验证，就仍是候选。震屏、粒子和音效都可省略。

带着试玩问题来时，尽量说明发生的位置与操作。录屏、玩家原话和工具测量各有作用，智能体会区分证据与猜测，再给最小改动及复测办法。只有“有点无聊”也可以开始讨论，但不能凭这句话宣布病因已经找准。

只要分析就不改工程，明确要求修复则在授权范围内推进。小问题可以只答几句，不需要先给按钮开会。详见 [手感反馈](../references/feel-and-feedback.md) 和 [试玩诊断](../references/playtest-diagnosis.md)。

使用简报生成工具时，推荐填写 `experience`，旧 `loop` 仍可用。两者都有时采用 `experience`，所选内容不能为空。试玩表中不属于作品的项目可删除或标为不适用。
